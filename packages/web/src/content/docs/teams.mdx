---
title: Teams
description: Run multiple AI specialists on a single goal.
---

Teams let multiple AI specialists collaborate on a single goal. An orchestrator staffs a team, assigns work, triggers peer reviews, and converges on a result — all autonomously.

:::tip
Use teams for complex tasks that benefit from specialized perspectives — architecture decisions, full-feature implementation, or security-sensitive work.
:::

Teams run alongside the regular single-agent mode. Your existing sessions and workflows are unaffected.

---

## Watch progress

Team sessions integrate with the TUI sidebar and session navigation.

---

### Track TODOs

The orchestrator writes live progress to the TODO sidebar on your parent session. Phase progress appears as high-priority items, and agent tasks appear as medium-priority items.

As phases complete and agents finish their work, items update in real time.

```txt frame="none"
 Todo
  ✓ Phase: understanding
  ● Phase: design
  ○ Phase: implementation
  ○ Phase: verification
  ✓ [architect] Design system architecture
  ● [developer] Build REST API endpoints
```

---

### Navigate child sessions

Every agent runs in its own child session, linked to your calling session via `parentID`. The orchestrator session is also a child, so you can inspect its full conversation history.

- Use `session_child_cycle` to cycle through active agent sessions
- Use the back arrow to return to the parent session
- Child sessions stay out of the main session list sidebar

## Start a session

Run the `/team` command with a description of what you want done.

```txt frame="none"
/team Build a REST API for user management with auth, rate limiting, and tests
```

The orchestrator takes over. It staffs the right specialists, decomposes the work, and drives the team through to completion.

---

### Follow the execution

Here's what happens when you type `/team`:

1. The command template replaces `$ARGUMENTS` with your input and sends it to the LLM.
2. The LLM calls the `team` tool with your goal.
3. The tool calls `Team.start()`, which creates a session, an orchestrator, and a workspace.
4. The orchestrator runs in a loop — staffing agents, assigning tasks, triggering reviews, and advancing phases.
5. Each agent runs through `SessionPrompt.prompt()` with full tool access (bash, edit, write, etc.). After each turn, tool calls are extracted and recorded in the workspace.
6. If the team needs your input, the tool uses the question system to prompt you in the TUI.
7. When complete, the tool formats the results — including files modified and commands run — and the LLM summarizes them for you.

## Know the architecture

A team session has five layers.

| Layer            | What it does                                                    |
| ---------------- | --------------------------------------------------------------- |
| **Orchestrator** | Drives the loop — staffs agents, assigns tasks, advances phases |
| **Roster**       | Agent lifecycle — spawn, retire, track status and metrics       |
| **Workspace**    | Shared state — goal, plan, decisions, artifacts, questions      |
| **Messages**     | Typed communication graph between agents                        |
| **Reviews**      | Critique → revision loops with auto-escalation                  |

The orchestrator is the only agent that sees the full picture. Individual specialists see a filtered view based on the [sharing strategy](#choose-a-sharing-strategy).

Each agent runs through the standard `SessionPrompt.prompt()` pipeline with full tool access. After an agent finishes, the execution bridge extracts tool call results (file edits, bash outputs) and surfaces them to the orchestrator as workspace artifacts and status messages.

---

### Review the data model

Everything is persisted in SQLite across 5 tables with cascade deletes.

| Table            | Purpose                            | Key columns                                                  |
| ---------------- | ---------------------------------- | ------------------------------------------------------------ |
| `team_session`   | One row per team session           | `goal`, `phase`, `status`, `sharing_strategy`                |
| `workspace`      | Shared state sections (8 per team) | `section`, `content` (JSON), `version`, `last_updated_by`    |
| `agent_instance` | One row per spawned agent          | `role`, `expertise` (JSON), `relationships` (JSON), `status` |
| `team_message`   | Communication graph                | `from_role`, `to_role`, `type`, `content`, `ref_ids` (JSON)  |
| `review_thread`  | Review lifecycle tracking          | `author_role`, `reviewer_role`, `status`, `round`            |

Each table has a foreign key to `team_session` with `ON DELETE CASCADE`. Compound indexes cover the common query patterns.

## Understand the lifecycle

Every session flows through statuses and phases.

---

### Track the status

| Status         | Meaning                                  |
| -------------- | ---------------------------------------- |
| `active`       | Working                                  |
| `waiting_user` | Orchestrator escalated a question to you |
| `complete`     | All work is done                         |
| `cancelled`    | Session was cancelled                    |

When the orchestrator uses the `escalate` action, the session flips to `waiting_user`. After you answer, it returns to `active`.

---

### Move through phases

Every session progresses through five phases. The orchestrator controls transitions.

| Phase            | Step budget | Purpose                                    |
| ---------------- | ----------- | ------------------------------------------ |
| `understanding`  | 10          | Analyze the goal, clarify requirements     |
| `design`         | 15          | Architect the solution, make key decisions |
| `implementation` | 30          | Build it — code, configs, migrations       |
| `verification`   | 15          | Review, test, fix issues                   |
| `complete`       | —           | Wrap up and report results                 |

Budgets are measured in orchestrator steps. If a phase exceeds its budget, the orchestrator auto-advances to the next one. The total step limit across all phases is 100.

---

## Know the roles

Nine built-in role templates are available. The orchestrator picks the right ones based on your goal.

| Role                       | Expertise                                        | Has signals |
| -------------------------- | ------------------------------------------------ | ----------- |
| **Architect**              | System design, patterns, technical decisions     | No          |
| **Developer**              | Implementation, code quality, debugging          | No          |
| **QA**                     | Testing, verification, edge cases                | Yes         |
| **Security reviewer**      | Vulnerabilities, auth patterns, input validation | Yes         |
| **Performance specialist** | Optimization, profiling, scalability             | Yes         |
| **Database specialist**    | Schema design, migrations, query optimization    | Yes         |
| **DevOps**                 | Deployment, CI/CD, infrastructure                | Yes         |
| **UX reviewer**            | Usability, accessibility, WCAG compliance        | Yes         |
| **Documentation writer**   | Technical writing, API docs, user guides         | Yes         |

Each template defines a system prompt, workspace read/write permissions, and expertise tags. Every spawned agent gets its own OpenCode session as a child of the calling session.

---

### Understand signals

Roles with signals are auto-suggested through implicit signal detection. When an agent's output mentions terms like "security", "vulnerability", or "injection", the system suggests spawning a security reviewer.

A role needs at least 2 signal hits to be suggested. Roles without signals — architect and developer — are never auto-suggested and must be explicitly staffed.

---

### Register custom roles

Register your own role templates programmatically.

```ts title="custom-role.ts"
import { Roles } from "./team/roles"

Roles.register({
  role: "api-designer",
  prompt: "You are an API design specialist...",
  description: "REST/GraphQL API design and consistency",
  expertise: ["api design", "REST", "GraphQL", "OpenAPI"],
  workspaceRead: ["goal", "constraints", "plan", "decisions"],
  workspaceWrite: ["artifacts", "questions"],
  signals: ["api", "endpoint", "REST", "GraphQL", "OpenAPI"],
})
```

The `workspaceRead` and `workspaceWrite` arrays control which workspace sections the agent can access. The `signals` array drives auto-suggestion. Registered roles appear in `Roles.list()` and are matchable via `Roles.match()`.

## Know the actions

The orchestrator drives the team by emitting one JSON action per turn. There are 11 actions.

| Action     | Key fields           | Purpose                                             |
| ---------- | -------------------- | --------------------------------------------------- |
| `staff`    | `roles[]`            | Spawn multiple agents and assign initial tasks      |
| `assign`   | `role`, `task`       | Give a task to an existing agent                    |
| `spawn`    | `role`, `reason`     | Add a single new specialist to the roster           |
| `retire`   | `role`, `reason`     | Remove an agent that's no longer needed             |
| `route`    | `from`, `to`         | Forward a question from one agent to another        |
| `decide`   | `description`        | Record an architectural or design decision          |
| `escalate` | `question`           | Ask the user a question when the team is stuck      |
| `advance`  | `phase`, `summary`   | Move to the next phase                              |
| `review`   | `author`, `reviewer` | Trigger a review loop between two agents            |
| `mediate`  | `review_id`          | Resolve an escalated review with a binding decision |
| `complete` | `summary`            | End the session with a summary                      |

Actions are parsed from JSON, optionally wrapped in a markdown code block. Invalid actions are retried.

---

### Follow composition guidelines

The orchestrator follows sizing heuristics from its system prompt.

- **Simple bug fix**: Developer + QA (2 agents)
- **Feature addition**: Architect + Developer + QA (3 agents)
- **Security-sensitive**: add Security Reviewer
- **Performance-critical**: add Performance Specialist
- **Database changes**: add Database Specialist

It starts minimal and spawns more agents as needed.

## Understand communication

Agents communicate through typed messages stored in the `team_message` table. There are 10 message types.

| Type            | Purpose                                         |
| --------------- | ----------------------------------------------- |
| `proposal`      | Agent proposes a design or approach             |
| `critique`      | Reviewer critiques an artifact                  |
| `question`      | Agent asks another agent a question             |
| `answer`        | Agent answers a question                        |
| `decision`      | Decision recorded by orchestrator               |
| `handoff`       | Orchestrator assigns work to an agent           |
| `status`        | Status update (phase change, completion, error) |
| `artifact`      | Code, config, or other output                   |
| `spawn_request` | Agent or system requests spawning a specialist  |
| `escalation`    | Question escalated to user or orchestrator      |

Messages can be targeted (agent-to-agent) or broadcast (to the whole team). Each message can carry `ref_ids` linking to review threads and `workspace_mutations` describing state changes.

---

### Know the output tags

Agents use tag-based structured output. The execution layer parses these from the LLM response.

| Tag                | Extracted to              | Purpose                         |
| ------------------ | ------------------------- | ------------------------------- |
| `[PROPOSAL]`       | `proposals[]`             | Design or architecture proposal |
| `[QUESTION: role]` | `questions[]`             | Ask a specific agent a question |
| `[CONCERN: topic]` | `concerns[]`              | Flag a concern for the team     |
| `[ARTIFACT]`       | `artifacts[]`             | Code, config, or deliverable    |
| `[SPAWN: role]`    | `spawnRequests[]`         | Request a specialist be added   |
| `[CRITIQUE]`       | `critiques[]`             | Review feedback on an artifact  |
| `[COMPLETE]`       | `complete` flag + summary | Agent signals task is done      |
| `[APPROVED]`       | `approved` flag           | Reviewer approves the artifact  |

Tags are case-insensitive. Each tag's content extends to the next tag or end of text.

---

### Know the tool extraction

In addition to text tags, agents make real file changes and run commands through tools. Tool calls are automatically extracted after each agent turn and recorded in the workspace `artifacts` section as `modified_files` and `commands_run`.

The orchestrator sees a summary of tool activity in its context. File-modifying tools (`edit`, `write`, `patch`, `apply_patch`) have their file paths extracted. Bash commands are captured with their output. The `multiedit` tool is tracked as a generic tool call.

---

## Use the workspace

The workspace is shared state organized into 8 sections, initialized when a session is created.

| Section        | Type   | Initial value       | Content                         |
| -------------- | ------ | ------------------- | ------------------------------- |
| `goal`         | string | User's request      | The original task description   |
| `constraints`  | array  | `[]`                | Boundaries and requirements     |
| `plan`         | object | `{status: "draft"}` | Architecture and task breakdown |
| `tasks`        | array  | `[]`                | Work items with status tracking |
| `decisions`    | array  | `[]`                | Decisions with rationale        |
| `questions`    | array  | `[]`                | Open and answered questions     |
| `artifacts`    | object | `{}`                | Code, configs, and outputs      |
| `agent_states` | object | `{}`                | Per-agent working state         |

Each section is versioned and tracks who last updated it. The workspace supports `get`, `set`, `append`, and `remove` operations.

---

### Track decisions

Decisions have a structured format with rationale and alternatives.

```json
{
  "id": "wks_01jnb...",
  "description": "Use JWT with httpOnly cookies",
  "rationale": "Stateless, works with CDN, secure against XSS",
  "alternatives": ["Session-based auth", "OAuth tokens in localStorage"],
  "made_by": "architect",
  "status": "approved",
  "timestamp": 1740067200000
}
```

Decisions can have a status of `proposed`, `approved`, or `rejected`. The orchestrator records decisions via the `decide` action.

---

### Route questions

Questions are tracked with routing and status.

```json
{
  "id": "wks_01jnb...",
  "question": "Should we use separate tables for credentials?",
  "asked_by": "developer",
  "routed_to": "architect",
  "status": "open"
}
```

Questions can be `open`, `answered`, or `escalated`. The orchestrator uses the `route` action to assign a question to the right specialist, then assigns that agent to answer it.

## Choose a sharing strategy

Sharing strategies control what each agent sees and how their outputs propagate back to the workspace. The default is `selective`.

---

### Use selective

Each agent sees:

- The full workspace **summary** (a rendered text overview)
- **Detailed content** for sections they have read access to (empty sections are excluded)
- **Messages** addressed to them, from them, or broadcast (up to 10)
- **Active reviews** they're involved in
- **All decisions**

On propagation, collaborators and reviewers are notified. Write permissions are enforced — agents can only update sections listed in their `workspaceWrite`. Only `set` and `append` operations are applied; other operations pass through without modifying data.

---

### Use hierarchical

Each agent sees:

- A **workspace overview** (summary only)
- **Detailed content** for sections they have read access to
- A notice to route all questions through the orchestrator

No messages or reviews are injected. The orchestrator curates all information flow. On propagation, only the orchestrator is notified.

---

### Use broadcast

Every agent sees:

- The **full workspace** — all 8 sections in detail (empty sections excluded)
- **All recent messages** (up to 20)
- **All active reviews**
- The **full roster** with status and expertise

On propagation, all agents except the author are notified. Write permission checks are skipped.

---

## Understand reviews

The review protocol ensures quality through structured critique-revision loops.

---

### Know the flow

1. The orchestrator triggers a review with `{"action": "review", "artifact": "...", "author": "developer", "reviewer": "architect"}`.
2. The reviewer receives the artifact plus the `reviewer-instructions` prompt.
3. The reviewer responds with `[APPROVED]` (done) or `[CRITIQUE]` (needs work).
4. If critiqued, the author receives the critique plus the `revision-instructions` prompt.
5. The author responds with a `## Revision Summary` and an `[ARTIFACT]` block.
6. Steps 2–5 repeat for up to **3 rounds**.
7. If the review doesn't converge after 3 rounds, it's **auto-escalated** to the orchestrator for mediation.

---

### Track review status

| Status           | Meaning                                        |
| ---------------- | ---------------------------------------------- |
| `active`         | Review is in progress                          |
| `approved`       | Reviewer signed off                            |
| `needs_revision` | Critique recorded, waiting for author revision |
| `escalated`      | 3 rounds without convergence, needs mediation  |

The orchestrator can mediate escalated reviews using the `mediate` action. Operations on non-existent reviews are safe no-ops — they return `undefined` and don't emit events.

---

## Track agent status

Every agent on the roster has a status the orchestrator monitors.

| Status    | Meaning                       |
| --------- | ----------------------------- |
| `idle`    | Ready for new work            |
| `working` | Currently executing a task    |
| `waiting` | Blocked on input from another |
| `retired` | Removed from the team         |

Retired agents are excluded from active lookups but remain in the database. The roster also tracks `steps_used` and `tokens_consumed` per agent.

---

### Understand retirement

The `shouldRetire` function checks whether an agent can be safely removed. An agent won't be retired if it's `working`, already `retired`, or involved in an active review as either author or reviewer.

A `waiting` or `idle` agent with no active reviews will be flagged for retirement.

---

## Listen to events

Teams emit 14 events through the bus system. Subscribe to these in plugins.

---

### Review the event list

**Session lifecycle:**

- `team.created` — new session started (payload: `{ info: Team.Info }`)
- `team.updated` — session status changed (payload: `{ info: Team.Info }`)
- `team.completed` — session finished (payload: `{ info: Team.Info, summary: string }`)

**Orchestrator:**

- `team.phase_changed` — phase transition (payload: `{ teamSessionID, phase }`)
- `team.decision` — decision recorded (payload: `{ teamSessionID, decision: Workspace.Decision }`)
- `team.escalated` — question escalated to user (payload: `{ teamSessionID, question }`)

**Agent lifecycle:**

- `team.agent.spawned` — agent joined the roster (payload: `{ info: Roster.Info }`)
- `team.agent.retired` — agent removed (payload: `{ info: Roster.Info }`)
- `team.agent.updated` — agent status changed (payload: `{ info: Roster.Info }`)

**Communication:**

- `team.message` — message sent between agents (payload: `{ info: TeamMessage.Info }`)

**Workspace:**

- `workspace.updated` — section changed (payload: `{ teamSessionID, section, updatedBy? }`)

**Reviews:**

- `team.review.started` — review thread created (payload: `{ info: Review.Info }`)
- `team.review.completed` — review approved (payload: `{ info: Review.Info }`)
- `team.review.escalated` — review hit max rounds (payload: `{ info: Review.Info, reason }`)

## Use the API

The feature is primarily accessed via the `/team` command. For programmatic use, the `Team` namespace and `team` tool are also available.

---

### Know the tool

The `team` tool is registered in the tool registry and callable by any LLM agent. It accepts two parameters.

| Parameter          | Type   | Required | Default       | Description                                 |
| ------------------ | ------ | -------- | ------------- | ------------------------------------------- |
| `goal`             | string | Yes      | —             | The task for the team                       |
| `sharing_strategy` | enum   | No       | `"selective"` | `selective`, `hierarchical`, or `broadcast` |

When the team needs user input, the tool uses the question system to prompt you in the TUI. The tool returns a formatted summary with the final phase, roster, files modified, commands run, and recent activity.

---

### Call start directly

`Team.start()` creates a session and runs the orchestrator loop to completion.

```ts
const result = await Team.start({
  goal: "Build a REST API with auth",
  sharingStrategy: "selective",
  parentSessionID: ctx.sessionID,
  onEscalate: async (question: string) => {
    return "Use JWT with httpOnly cookies"
  },
  onStatus: (message) => console.log(message),
  abort: controller.signal,
})

// result.teamSession — the final Team.Info
// result.summary — completion summary string
```

The `parentSessionID` threads through to all spawned agent sessions, making them children of the calling session. This enables TUI navigation between agent sessions and keeps them out of the main session list.

The `onEscalate` callback fires when the orchestrator uses the `escalate` action. The session status flips to `waiting_user` until you return an answer.

---

### Inspect a session

`Team.status()` returns the current state of a session.

```ts
const status = Team.status(teamSessionID)
// status.info — session metadata (phase, status, strategy)
// status.roster — active agents with role, status, expertise
// status.recentActivity — last 10 messages (type, from, to, content)
// status.openQuestions — unanswered questions
// status.workspaceSummary — rendered workspace text
// status.modifiedFiles — files changed by agents
// status.commandsRun — bash commands executed by agents
```

Returns `undefined` for non-existent sessions. When `artifacts` exist but contain no `modified_files` or `commands_run`, empty arrays are returned.

---

### Cancel a session

`Team.cancel()` retires all agents, sets the status to `cancelled`, and emits a `team.updated` event.

```ts
Team.cancel(teamSessionID)
```

## Try it out

Restart the OpenCode server and TUI to pick up the new tool registration, migration, and command template.

```txt frame="none"
/team Build a simple utility function that validates email addresses with tests
```

:::caution
The session may take several minutes depending on task complexity and model speed. Each agent runs its own LLM calls sequentially through the orchestrator loop.
:::

Watch for these steps in the output:

1. **Tool call** — the LLM calls the `team` tool with your goal
2. **Staffing** — the orchestrator spawns agents (likely Architect + Developer + QA)
3. **Phase progression** — understanding → design → implementation → verification → complete
4. **Review cycles** — critique → revision exchanges between agents
5. **Completion** — a summary with the roster and recent activity

If the team needs your input, you'll see a question prompt in the TUI.

### Know what's not tested

Functions that call `SessionPrompt.prompt()` need a real LLM provider and can't be unit tested. These are:

- `Execute.run()` — runs an agent against the LLM
- `Orchestrator.run()` — the main orchestrator loop
- `ReviewLoop.run()` — the critique-revision cycle
- `Team.start()` — creates a session and runs the orchestrator

`Roster.spawn()` is fully tested — it creates real sessions via `Session.create()` and verifies parent-child relationships, session titles, and bus event emission.

---

### Know the test patterns

Tests use `Instance.provide({ directory, fn })` for database access, with `test/preload.ts` for isolation. No mocks — tests run against real SQLite with real migrations.

Helper functions like `createTeamSession()` insert directly into tables via `Database.use()` to avoid triggering full creation flows. Bus events are verified with `Bus.subscribe()` and a short `setTimeout` to allow delivery.

bun test test/team/workspace-comprehensive.test.ts
